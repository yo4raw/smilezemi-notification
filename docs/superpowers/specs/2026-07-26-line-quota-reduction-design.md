# LINE通知の送信数削減（夜通知の条件送信）+ 429ハンドリング改善 設計

日付: 2026-07-26
ステータス: 承認済み（同日改訂）

## 背景・問題

2026-07-26 朝通知の GitHub Actions run が LINE API `429 Too Many Requests` で失敗した。

調査で確定した事実:

- 送信先 `LINE_USER_ID` は家族4人グループ。LINE Messaging API はグループへの push を「メッセージ数 × グループ人数」でカウントするため、**1通知 = 4カウント**
- 通常日は朝+夜で 8カウント/日、週間レポートのある月曜は 12（insight API 実績と一致）
- 無料プラン（コミュニケーションプラン）の月間上限は 200。7/25 時点で 197 消費しており、7/26 朝の送信（4カウント必要）が拒否された
- 朝夜通知の月間消費は約248カウントで、無料枠200を構造的に超過する（今月限りの事故ではない）
- コードのバグではない。429 発生時もストリーク確定とキャッシュ保存は成功しており、データ喪失はない

## 廃案: 2チャンネル分離

当初、朝通知用に2つ目のMessaging APIチャンネル（Smilebot2）を作成し枠を倍にする設計を採用・実装したが、**LINEの仕様で1つのグループに公式アカウント（bot）は1つしか参加できない**ことが判明し廃止した。Smilebot2 は未使用（GitHub Secret `LINE_CHANNEL_ACCESS_TOKEN_MORNING` は削除済み）。

## 対策方針（承認済み）

チャンネルは既存の1つのまま、**夜通知を条件送信にして月間消費を200以内に抑える**。

### 夜通知の条件送信

夜通知（`src/index.js`、当日速報）は「**このままだと今日のストリーク記録を更新できないユーザーが1人でもいる日**」だけ送信する。全ユーザーが当日のストリーク要件（小学生: ミッション4、中学生: 曜日別3/5）を達成済みの日は、夜のうちに促す価値がないため送信しない。確定情報は翌朝の朝通知が毎日必ず届ける。

- 判定は既存の `isStudied(user, { minCompletedMissions: getRequirementForCourse(...) })`（当日暫定+1表示と同じロジック）を全ユーザーに適用し、1人でも false なら送信
- `dataReliable: false`（詳細取得失敗）のユーザーは完了数が0に見えるため未達扱いになる = 送信される（安全側: 通知が出る方向に倒す）
- 送信しない日も `saveData` は実行し、翌日の差分比較の基準を保つ。DRY_RUN 時は従来どおり保存もしない
- 朝通知・週間レポート・月次ボーナスは無条件送信のまま変更なし

### 月間消費の見積もり

| 通知 | 頻度 | 月間カウント |
|---|---|---|
| 朝通知 | 毎日 | 31×4 = 124 |
| 週間レポート | 毎週月曜 | 〜5×4 = 20 |
| 月次ボーナス | 毎月1日 | 4 |
| 夜通知 | 未達ユーザーがいる日のみ | 残枠 〜52 = **月13日分まで** |

**受容済みリスク**: 全員未達の日が月13日を超えると月末に再び429になる。子供たちが日々達成していれば夜通知はほぼ発生しない前提の設計。429時は改善後のログ（下記）で即座に原因が分かる。

## 変更内容

### 1. `src/index.js` — 夜通知の条件送信

ストリーク表示ループで各ユーザーの `todayStudied` を集計し、全員 true なら送信をスキップして `saveData` のみ実行して正常終了する。

### 2. `src/notifier.js` — 429ハンドリング改善（実装済み）

- **429 は即時失敗**: 月間上限超過はリトライで解決しないため、401 と同様にリトライしない
- **エラーレスポンスボディをログに含める**: LINE API が返す理由（`"You have reached your monthly limit."` 等）をエラーメッセージに含める（`maskTokenInError` でマスキング）。ボディが読めない場合は status のみで続行

### 3. テスト

- `tests/notifier.test.js`: 429非リトライ・ボディ記録・ボディ欠落耐性（実装済み）
- `tests/index.test.js`: 全員達成日はsendPushMessageを呼ばずsaveDataは呼ぶ / 未達者が1人でもいれば送信 / DRY_RUN+全員達成は保存もしない

### 4. `.github/workflows/morning-crawler.yml`

2チャンネル分離時の変更（`LINE_CHANNEL_ACCESS_TOKEN_MORNING` 参照）を元に戻す。

### 5. ドキュメント（`CLAUDE.md`）

送信数の制約（グループpushは人数分カウント・月200枠）と夜通知の条件送信仕様を記載。

## エラー処理・エッジケース

- ストリークデータ読み込み失敗時: 全ユーザー `createInitialState()`（streak 0）扱いだが、送信要否は当日の完了数だけで決まるため影響なし
- 既存チャンネルの7月末までの429: 枠が尽きているため**全通知が7/31まで失敗**する（8/1に自動復旧）。runは赤くなるがキャッシュ保存は `if: always()` でデータは保全される

## 検証

- `npm test`（追加テスト含む）と `npm run lint` が通ること
- `DRY_RUN=true node -r dotenv/config src/index.js` で送信要否判定が正しく動くこと
- 8/1以降のスケジュール実行で朝通知が復旧し、夜通知が全員達成日にスキップされることをログで確認
