# スケジュールワークフロー自動無効化の防止（Keepalive）設計

作成日: 2026-10-08

## 背景と目的

このリポジトリは公開リポジトリで、通知システム（夜通知・朝通知・月次清算）の実行はすべて GitHub Actions の `schedule` トリガーに依存している。GitHub は**公開リポジトリで60日間リポジトリに活動がないと、schedule ワークフローを自動で無効化する**。無効化されると cron が発火しなくなり、通知システム全体が何もしないまま止まる。

日常運用（ストリーク確定・免除日の操作など）は Turso をローカルから直接読み書きするため、リポジトリへのコミットなしに何ヶ月も運用が継続しうる。つまり「コードが完成して安定運用に入った」状態が最も無活動になりやすく、このリポジトリは無効化の条件に自然に近づく構造になっている。

**達成したい状態**: 人手を介さず、リポジトリの活動が60日を越えて途切れないこと。万が一無効化されても自律的に復旧すること。

## スコープ

### やること

- `.github/workflows/keepalive.yml` を新規作成する
  - 月2回（毎月1日・15日 UTC 03:35）の schedule + workflow_dispatch
  - 最終 push から45日以上経過していれば空コミットを push する
  - `disabled_inactivity` 状態のワークフローを API で再有効化する
  - 失敗時は既存パターン（LINE→失敗時のみDiscord）で通知する

### やらないこと

- **外部 keepalive アクションを使わない**。`gautamkrishnar/keepalive-workflow` などは存在するが、サードパーティアクションへの依存を増やさず、`gh` CLI と `git` だけで同等機能を実装する（このリポジトリは外部 action を checkout/setup-node 等の公式系に限定している）
- **無条件の定期コミットはしない**。45日ルールで条件付きにし、コミット履歴を汚さない。直近45日以内に人のコミットがあれば何もしない
- **手動無効化（`disabled_manually`）のワークフローには触らない**。意図的な無効化を勝手に戻さない
- **PAT（個人アクセストークン）は使わない**。`GITHUB_TOKEN` のみ。トークン管理・失効リスクを増やさない

## 設計

```text
keepalive.yml（毎月1日・15日 UTC 03:35 起動）
   ├─ Step1: gh api repos/{repo} → pushed_at を取得
   │         45日以上経過 → git commit --allow-empty → push origin HEAD:main
   │         45日未満     → スキップ
   ├─ Step2: gh api .../actions/workflows → state == "disabled_inactivity" を抽出
   │         あれば PUT .../workflows/{id}/enable で再有効化
   └─ 失敗時: run-in-docker.yml と同じ LINE→Discord 失敗通知
```

### 判断ポイント

- **空コミットの push は「活動」としてカウントされる**。`GITHUB_TOKEN` による push は新規 workflow 実行をトリガーしない（無限ループ防止の仕様）が、無効化判定の活動には含まれる。`[skip ci]` を付けてCI（`ci.yml` の push トリガー）への影響も明示する
- **45日閾値・月2回起動**: 60日の猶予に対し、cron 実行が1回スキップ・遅延されても次回でリカバーできる余裕を持つ。GitHub の schedule は数時間遅延・稀にドロップする実績があるため月1回は避けた
- **再有効化ステップは保険**。keepalive のコミット自体が活動を維持するので通常は到達しないが、手動操作や長期の全体無効化からの復旧を自動化する。自分自身が無効化された場合はこのワークフローも動かないため、その場合のみ手動で1度再有効化する（以降は自律復旧する）
- **必要な権限は `contents: write` + `actions: write`**。既存ワークフローは `contents: read` のみだが、このワークフローは push とワークフロー再有効化が本体機能なので昇格が必須
- **失敗通知を付ける理由**: keepalive が壊れたまま60日を越えると通知システム全体が静かに死ぬ。通知手段そのものなので「最後の砦」パターンをそのまま流用し、失敗は必ず表面化する
- **実行は Docker なしの ubuntu-latest 直実行**。クロールも.envも不要で、数秒で終わる。`run-in-docker.yml` の共通手順（待機・ビルド・シークレット検証）は不要なので通さない

## 既知の制約

- keepalive ワークフロー自身が `disabled_inactivity` になった場合、自己復旧はできない（無効化されたワークフローは実行されないため）。その場合は1度だけ手動で再有効化すれば、以降の起動で他ワークフローも自動復旧する。無効化前にGitHubからメール通知が来るため、検知手段はある
- 空コミットの push が他プロセスの push と競合した場合、その回は失敗するが次回（最大15日後）にリトライされる。失敗通知で表面化する
- schedule の大幅遅延（GitHub 側障害）が半月続くと理論上60日を越えうるが、その場合でも再有効化ステップと失敗通知で復旧・検知できる

## 検証

- YAML 構文: ローカルでパース確認済み
- run ブロック: `bash -n` で構文確認済み
- 実動作はマージ後に `workflow_dispatch` で手動実行し、ログで「45日未満のためスキップ」または push 成功を確認する（pushed_at が直近ならスキップ経路になるのが正常）
