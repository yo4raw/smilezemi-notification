# ボーナスポイント機能 + 月次清算通知ワークフロー 設計書

作成日: 2026-07-13
ステータス: ユーザー承認済み(清算方式・日次表示・通知時刻の3点を質疑で確定)

## 要件

1. おたすけは3までしか貯められないため、上限を超えた分(10日マイルストーンの+1)をボーナスポイントとして貯める
2. ボーナスポイントは月末に清算し、お小遣いとして現金で支給する
3. 毎月1日の朝に子供たちそれぞれのボーナスポイントを通知するワークフローを追加する

## 確定した仕様判断

| 論点 | 決定 |
|------|------|
| 清算方式 | 毎月1日の通知と同時にボーナスを0にリセット。新しい月は0から積み直す |
| 日次表示 | ボーナス1以上のときだけ夜・朝通知のストリーク行に表示 |
| 通知時刻 | JST 8:00ごろ(朝通知7:00の後。前月最終日の確定分を含めて清算) |

## 設計

### 1. ボーナス獲得ルール (`src/streak.js`)

- 状態に `bonus` フィールドを追加。既存データ(v1.2)に無い場合は0として扱い(`?? 0`)、次回保存時に書き込まれる。**バージョン変更は不要**
- `createInitialState()` に `bonus: 0` を追加
- `confirmDay` のマイルストーン判定を拡張: 連続10日到達時、
  - おたすけが上限(3)未満 → 従来どおりおたすけ+1(event: `milestone`)
  - おたすけが上限 → **ボーナス+1**(event: `bonus`、新設)
- ボーナスは全分岐(学習・おたすけ消費・リセット・streak0ガード)で保持される。**リセットでも消えない**(支給予定のため)。月次清算でのみ0になる
- 清算用の純粋関数 `settleBonuses(streakUsers)` を追加: 全ユーザーの `bonus` を0にした新しいマップと、清算リスト `[{userName, bonus}]` を返す(入力は変更しない)

### 2. 日次通知の表示 (`formatStreakInfo`)

- ボーナス1以上のとき、ストリーク行末尾に `💰 ボーナス: {N}P` を追記
- event `bonus` のお祝い行: `🎉 {streak}日連続達成!おたすけ満タンのためボーナス+1(合計{N}P)`
- notifier.js は無変更(ストリーク行は formatStreakInfo が生成)

### 3. 月次清算エントリポイント (`src/monthly-bonus-index.js`)

クロール不要のため**ブラウザを起動しない**。依存は config / streak / notifier のみ(playwright非依存)。

処理フロー:
1. `loadConfig`(失敗時 exit 1)
2. `loadStreakData`(失敗時は障害通知を送って exit 1。**リセットしない**)
3. `settleBonuses` で清算リストとリセット済みマップを生成
4. メッセージ生成(前月ラベルはJST基準で算出。0ポイントの子も表示):

```
💰 ボーナスポイント清算(7月分)

👤 吉岡祥吾さん: 2ポイント
👤 吉岡千晴さん: 0ポイント

ボーナスポイントはお小遣いとして支給してね!
```

5. `DRY_RUN=true` ならプレビュー表示のみ(送信・保存なし)
6. `sendPushMessage` で送信。**送信成功時のみ** リセット済みマップを `saveStreakData` で保存(送信失敗時は清算を持ち越し、次回実行で再清算できる)
7. 対象ユーザーが0人の場合も「対象がいません」の旨で通知する(死活確認を兼ねる)

### 4. ワークフロー (`.github/workflows/monthly-bonus.yml`)

「毎月1日 JST 8:00」はUTCでは前月末日23:00のため、cronで「1日」を直接指定できない。月末候補日起動+JST日付ガードで実現する。

- cron: `47 22 28-31 * *`(UTC 22:47 = JST翌日7:47。月末日に起動した場合のみJSTは「1日」になる)
- **JST日付ガード**: 起動時にJSTの日が「01」でなければ即・正常終了(月に3〜4回の空振りは数秒で終了)。`workflow_dispatch` はガードをスキップして常に実行
- JST 8:00まで待機(遅延起動時は即実行)
- **キャッシュrestoreは待機の後**に行う(朝通知の保存(〜7:05頃)との競合ウィンドウを最小化)。整合性チェック・save・失敗時LINE通知・.env削除は既存ワークフローと同一パターン
- 実行: `docker compose run --rm crawler node src/monthly-bonus-index.js`(既存パターン踏襲)
- permissions: `contents: read` + `actions: read`(整合性チェック用)

既知の残余リスク: 朝通知が大幅遅延した場合(保存が8:00以降)、その日の朝の確定分がボーナス清算に含まれない可能性がある(翌月に持ち越されるだけで消失はしない)。ワークフロー間の完全な直列化(concurrencyグループ)は別課題として扱う。

### 5. 挙動が変わる点

おたすけ満タン時の10日マイルストーンは、現在「何も起きない(+1が消滅)」→「ボーナス+1」になる。過去分の遡及付与はない。

## テスト

- `tests/streak.test.js`: bonusイベント境界(grace 3+10日到達→bonus+1・grace据え置き・event `bonus` / grace 2なら従来どおりmilestone)、各分岐でのbonus保持(grace_used・reset・streak0ガード・非マイルストーン学習日)、bonus欠損データ(`undefined`)の0扱い、`settleBonuses`(リセット・清算リスト・純粋性)、`formatStreakInfo`(1以上で表示・0で非表示・bonusお祝い行)
- `tests/monthly-bonus-index.test.js`(新規): require.cacheモック方式(playwright不要)。メッセージ内容(前月ラベル・各ユーザー・0P表示)、送信成功時のみリセット保存、送信失敗時は保存しない+exit 1、DRY_RUN時は送信・保存なし、loadStreakData失敗時は障害通知+exit 1
- ワークフロー: actionlintで構文検証。JST日付ガードのシェルはローカルで動作確認
